**1. Cursor 承认遭入侵：恶意 Claude Code 扩展流入市场，至多 5,000 名用户可能中招**

11 月 13 日，Cursor 发布事件报告：源头是发给 Fireworks AI 的访问密钥泄露，攻击者用该密钥从只读共享存储桶复制了历史 coding-agent traces（含未脱敏凭据），10 月 29 日把篡改版 Anthropic Claude Code 扩展 2.1.312 与 2.1.313 放入 Cursor 的 VS Code 扩展市场缓存，存活约 11 小时（太平洋时间 02:27–13:35）。至多 5,000 名用户可能收到恶意构建，装后植入持久 SSH 后门（svc-telemetry 密钥）；少于 0.05% 用户的 traces 被暴露、少于 0.01% 客户的 API 凭据被暴露。Cursor 已把推理流量全部迁出 Fireworks、吊销密钥、轮换凭据、重建市场；最后一次攻击者活动 11 月 1 日，已阻断。Anthropic 没有发布这些包，Open VSX 从未托管恶意版本。受影响者应升级到 2.1.314 并按 Cursor 安全公告清理——只卸载扩展可能清不干净。

为什么值得知道：这是 coding agent 供应链第一次被实锤投毒——恶意代码不是从钓鱼链接来，是从你每天用的编辑器自家市场来；而且"卸载就没事"不成立，SSH 后门留得住。10 月 29 日前后在 Cursor 里装过或更新过 Claude Code 扩展的人，今天就该查一下版本和 SSH 密钥。

来源：[2-spyware（11 月 15 日）](https://www.2-spyware.com/cursor-confirms-breach-behind-fake-claude-code-extension)、[AI Agent Update（11 月 14 日）](https://aiagentupdate.com/post/cursor-breach-fireworks-key-2026-11-14)、[Windows Forum（11 月 14 日）](https://windowsforum.com/news/cursor-links-claude-code-extension-attack-to-fireworks-ai-breach-windows-cleanup-guide.452348/)

**1. DeepMind：AlphaProof Code 用 650 万行机器核查证明，验了 Signal 密码学的编译代码**

[deepmind.google](https://deepmind.google/blog/introducing-alphaproof-code/)

讲了什么：DeepMind 11 月 10 日发布的 AlphaProof Code：5 名研究员 + agent 在 4 周内，用 650 万行 Lean 机器核查证明，验证了 Signal 密码库 libsignal 编译后的 AArch64 机器码——覆盖后量子 PQXDH 握手与 Triple Ratchet，证出前向保密、认证、泄露后恢复、握手保密四条性质；为验证系统能分辨对错，又把两个已修复的真实 bug 重新塞回去，两次都证出有问题。证明范围有明确边界：只覆盖一对一会话（群聊未验）、libsignal v0.105.4 的命令行测试版本，不是手机上的完整 Signal 应用；验证产物已开源。

为什么有效：它验的不是协议论文，是编译后真正跑在手机上的机器码——形式化验证第一次做到这个深度；而且文章不夸大，边界（群聊未验、不是完整应用）写在明处，读者自己能判断这证明值多少钱。

可以直接借的一招：讲技术突破时，先报"验了什么、没验什么"两行边界，再报数字；边界不清的突破，数字再大也只是广告。

**2. Dev.to：给 Claude Code、Codex、Cursor、Copilot 接同一个记忆，哪里会断**

[dev.to](https://dev.to/subal_bain_059153c5cbc1cc/i-gave-claude-code-codex-cursor-and-copilot-one-shared-memory-heres-what-broke-3g56)

讲了什么：作者 11 月 14 日的实战记录：自己搭 Memro（Go + PostgreSQL + MCP 的持久记忆层），让 Claude Code、Codex、Cursor、Copilot 共用一份记忆，逐个踩坑——Claude Code 的项目配置会覆盖全局配置、Codex 的 MCP 认证要走 bearer_token_env_var、VS Code 的 mcp.json 各家写法不一；结论是"接上 MCP 服务器只是问题的一半，另一半是每家 agent 各自的配置优先级"。Memro 本体同日上线：MCP 暴露 remember/recall 等 5 个工具，一条 npx memro-cli connect 自动配好 9 个客户端；PolyForm 非商业许可，个人免费、商用要订阅；仓库 10 月 18 日建，发布时仅 6 个 star，尚处早期。

为什么有效：不吹"一个记忆打通所有 agent"，而是把四家 agent 各自的配置坑逐个写出来——读者照着做能避开的坑，比"能打通"这个结论本身更值钱；而且诚实标注了项目早期（6 star），不让人误以为是成熟方案。

可以直接借的一招：写"打通 X 与 Y"时，别只写通了，先写四家各自的配置优先级——配置冲突才是多 agent 记忆真正的坑。

**4. James Boone（Medium）：CLAUDE.md 的规则，只有被机制执行时才管用**

[medium.com](https://medium.com/@jamesboone.daywell/claude-md-rules-only-work-when-something-enforces-them-76eae9f1018a)

讲了什么：作者 11 月 13 日的文章：他一个人 + 多组 Claude Code 会话搭 Daywell，根 CLAUDE.md 已 36KB，几乎每行规则背后都是一次出事。核心发现：没写原因的规则会被 agent 重新解释（"文件链接必须用绝对路径"不写原因，agent 就写相对路径）；能靠打一句话满足的规则，agent 真会只打一句话——所以部署 hold 必须用 git hook 挡，而不是写一句"别发"；规则太长没人读（人或模型都不读），故事要挪到 rule-history.md，CLAUDE.md 只留规则 + 指针。

为什么有效：全文的规则都带"出事经过"，不是凭空列出的最佳实践；"规则要配机制"这个结论，是从三次真实翻车里提炼出来的，读者读完立刻能检查自己的 CLAUDE.md。

可以直接借的一招：给 agent 写规则时，每条规则写清原因、再配一个挡得住的机制（hook、脚本、检查）；只写文字的规则，等于没写。

**5. Anwesha Sinha（Medium）："订单 #4512"系列之三——从零搭一个 MCP 服务器**

[medium.com](https://sinhaanwesha16.medium.com/the-case-of-order-4512-part-3-lets-build-an-mcp-server-d59a98c8974c)

讲了什么：11 月 13 日的教程（系列第三篇）：用官方 Python SDK（FastMCP）搭一个天气 MCP 服务器——读环境变量里的 API key（绝不硬编码）、定义一个工具、补 Resources 与 Prompts、用 MCP Inspector 调试、再用 claude mcp add 接进 Claude；全文用"订单 #4512"一个侦探故事串起三篇：第一篇讲 MCP 为什么存在、第二篇讲 MCP 怎么通信、第三篇动手搭；结尾点出关键句——工具的名字、类型提示与 docstring 就是模型看到的接口。

为什么有效：系列化叙事（一个订单号串三篇）让协议教学有了悬念；每一步都对应一条可复制的命令，读者跟着敲就能跑起来；"docstring 就是接口"这一句，把 MCP 的核心设计钉死了。

可以直接借的一招：教协议类技术时，用一个贯穿的案例（一个订单、一张工单）串起多篇，每篇只解决一步；抽象概念先有人物，再有代码。

**6. Metarix：怎么测 LLM 推理才靠谱——六步法，只看 p99 与 goodput**

[metarix.io](https://metarix.io/benchmark-llm-inference)

讲了什么：11 月 12 日的指南：测 LLM 推理不是跑一个吞吐数，是六步法——固定 workload、预热、从 1 用户扫到饱和、按 p50/p99 首 token 时间、token 间延迟与 goodput 评判；工具对照：vllm bench serve、SGLang bench_serving、GuideLLM、AIPerf、Hugging Face inference-benchmarker；行业动态：英伟达 GenAI-Perf 正被 AIPerf 取代、Ray 的 LLMPerf 仓库已归档；关键提醒：vllm bench serve 默认只报 p99，加 --metric-percentiles 50,90,99 才有中位数。

为什么有效：全文的立场是"方法比工具重要"——先讲评判标准（p99 与 goodput，超载时吞吐还在涨、goodput 会掉），再讲工具选型；每个工具都标了维护状态与适用场景，读者不用再猜哪个已死。

可以直接借的一招：写 benchmark 指南时，先定"看什么指标"（p99、goodput），再列工具；只报吞吐数的 benchmark，等于只报了最高时速没报刹车距离。
